# 2026-10-01 — DadaGP arrives: protocol, validation, fitted weights, one GuitarSet run

DadaGP v1.1 arrived today (ProgGP did not). Branch `dadagp-fit`. Every run that produced a
reported number was pre-registered in a script or config committed before it ran, and every
prediction is reported below whether or not it held. Three of them did not.

## Stage 0 — setup

- The dataset was moved into `data/dadagp/`, which is gitignored: the repository is public
  and DadaGP is research-use-only.
- ADR 0016 accepted at X = 10, so the M2 target is oracle E2 ≥ 0.760. Its E3 guardrail was
  refreshed to the post-Phase-1.5 baseline (0.9970 / 0.9896); the old figure predated the
  barre-reach fix and the baseline itself would have failed it.

## Stage 1 — the data layer (ADR 0021)

- **Token format verified against the dadaGP encoder's own source:** `s1` is the highest
  string; a fret is `GP value + capo − drop shift`, so pitch survives but a capo'd or
  drop-tuned track's physical fingering does not, and the tokens do not say which tracks
  those are.
- **Plan correction:** no PyGuitarPro-0.6 environment is needed. The tokens carry string and
  fret directly; PyGuitarPro 0.11 is used once, in a throwaway environment, to read tunings.
- A token-only filter leaks capo'd songs at 2.9% (10 of 340 sampled), so the filter reads
  the original GP files instead: one 8-minute pass over all 26,181, zero parse errors,
  **22,034 songs cleared** — 19,995 training, 2,039 validation.
- 32 split entries are missing from the archive: folders differing only in case, collapsed
  on a case-insensitive filesystem.
- On real data the five most common chord shapes parse as C, Am, Em, F and E — the string
  mapping is right.

## Stage 2 — ADR 0011's rules on human tab (ADR 0022)

**Hypothesis (pre-registered): the span thresholds are too strict. Rejected.**

| on 16,769,383 human chord shapes | pass rate |
|---|---|
| chord rules, barre modelled | **0.9986** |
| chord rules, ADR 0011's original note count | 0.9794 |
| speed rule, as implemented | **0.8835** |
| speed rule, hand carried across open shapes | 0.8513 |

The chord rules are right and the barre rule was necessary. The **speed rule** is what is
wrong: in an exploratory follow-up, 82.6% of failing moves were three frets or fewer and
77.9% were between single notes, so the rule counts a finger reaching as the hand moving.
The cost model's movement term has the same flaw.

**Bug found on real data:** 11 songs contain `bfx:tempo_change:0`, which divided by zero.
The parser now keeps the current tempo and counts the glitch; a regression test pins it.

## Stage 3 — fitting the cost weights

The decoder is linear in its weights, so it is a linear-chain CRF; `fingering/fit.py` fits it
by maximum likelihood with exact gradients, checked against the oracle-verified
`log_partition`, a brute-force sum over paths and finite differences.

| | move | span | high | open_reward |
|---|---|---|---|---|
| hand-set | 1.0 | 1.0 | 0.1 | +0.25 |
| fitted, 600 training songs | 0.5772 | 0.7377 | 0.3767 | −1.1483 |

DadaGP validation, 300 songs, 529,932 notes: NLL per group 0.7676 → 0.4976; recovery of the
human fingering 0.6196 → 0.6456. **Prediction "move : high falls by an order of magnitude":
missed** — 120 : 1 → 18.4 : 1.

Exploratory, and the most important number of the stage: by part, the fitted weights go
**0.8097 → 0.6963 on clean guitar** and 0.5422 → 0.6251 on distorted. The pooled gain is
all distorted, 71% of the notes. The pre-registered adoption rule (pooled recovery improves)
was met, but **the fitted weights were not made the default**: a typical user records clean
or acoustic guitar. That ruling was made from validation, before GuitarSet.

## Stage 4 — temperature

On DadaGP validation, per-note NLL picks **T = 1.721**. Calibration error, computed as E5
computes it: hand-set 0.2689 → fitted 0.1431 → fitted and calibrated **0.0562**.
**Prediction "T is close to 1": wrong.** Path-level likelihood leaves per-note posteriors
overconfident. "Most of the gain is the weights": held, 59% to 41%.

## Stage 5 — GuitarSet, evaluated once

| | hand-set | fitted + T | |
|---|---|---|---|
| E2 oracle | 0.6599 | **0.6988** | +0.0389 |
| E2 end-to-end | 0.4318 | **0.4603** | +0.0285 |
| E3 chord shapes, oracle / e2e | 0.9970 / 0.9896 | 0.9961 / 0.9883 | **guardrail breached** |
| E5 end-to-end | 0.3851 | **0.1411** | −63% |

The original prediction held: E2 rises and the M2 target is missed, by 6.1 points. **The
revision I made from DadaGP's clean parts — "E2 will fall" — was wrong**: clean DadaGP is not
a good proxy for acoustic GuitarSet. The default does not change on this evidence; that
would be selecting on the test set. ADR 0023 records both legitimate routes.

## Judgement calls

- Taking "proceed" as sign-off on ADR 0016's X = 10.
- Filtering songs from the GP files rather than the tokens — it costs eight minutes and
  removes a measured 2.9% contamination.
- Not adopting the fitted weights despite the pre-registered rule being met, because of the
  clean-part loss. Cost if wrong: a better default sits unused until Ege decides.
- Recording a revised prediction before stage 5 rather than editing the original, so both
  are visible.
- Keeping E3's rules unchanged through stages 3–5, so every comparison is like for like.
