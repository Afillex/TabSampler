## What the review checked, and found sound

- **The split.** 60 and 300 tracks, disjoint, together the 360-track snapshot; a player
  with other than 60 tracks is refused. Only four code paths read GuitarSet: `eval-notes`
  (test, logged), `eval-m1` (test logged, validation not), `check-split` (counts only) and
  `scripts/measure_lattice.py` (player 00 only).
- **ADR 0038 was applied exactly.** Its rule is word for word the one committed in
  14a316d; the validation runs are stamped 14a316d, and their per-track files were written
  18–27 s after it. Recomputed from those files: oracle E2 +0.0232, 95% interval
  [−0.0030, +0.0513]; chord shapes 6543 → 6538 of 6607, a drop of 0.000757 against the
  0.0005 allowed. The exact chord-shape count fails the rule on its own, so the verdict
  does not depend on the bootstrap. Player 00's annotations hold 13,223 reference notes, as
  the ADR says.
- **T = 1.5728 reproduced.** `scripts/calibrate_temperature.py --decoder-config
  configs/phase1_baseline.yaml --split artist --part clean`, rerun: calibration error
  0.0884 at T = 1, 0.2153 at 2.9974 and 0.0941 at 1.5728 (NLL 0.7253 → 0.6433), as in
  `results.csv`. The script only prints, so no row was added.
- **The 300-track figures are never called a confirmation.** README, the 2026-10-03
  devlog, HANDOFF, ADRs 0037–0038 and `configs/m2_heldout_eval.yaml` all call them derived,
  or a baseline.
- **`results.csv` was only appended to**; all 43 earlier rows are byte-identical. The note
  on the two rows run with an uncommitted config is true: that config has not changed since
  8128105, and the run's E2 and E3 counts equal the hand-set run's exactly.
- ADRs 0003 and 0032 changed in their status lines only, which the ADR index allows.

## Found, and fixed (a commit each)

1. **Per-track counts for the 300 test tracks sat in `cache/validation/`**
   (`test300-default.json`, `test300-previous.json`). The two test runs wrote them though
   the plan did not ask for it, in the format `compare_validation.py` reads. Nothing shows
   they were used: no test-set interval appears anywhere. **Deleted, with Ege's approval.**
   `eval-m1` now refuses `--per-track-out` with `--split test` before anything is read or
   logged, and `compare_validation.py` refuses a file holding any test track (the new
   `splits.assert_no_test_tracks`). (7bab421)
2. **`eval-m1 --split` defaulted to `test`.** With every choice now made by
   `--split validation`, one forgotten flag would have read the test players. The flag is
   required, as DadaGP's scripts already require theirs, and `make eval-m1` passes
   `--split test`. (c2972bf)
3. **E1 figures from the two test sets were mixed.** The README quoted the 360-track E1
   (0.7437 / 0.7452) beside test-player figures (0.7493 / 0.7507) and said raw E1 "now"
   reproduces Phase 0. The 360-track history, the Phase 0 and M1 configs and HANDOFF now
   say that the gate commands read the 300 test tracks. (de5c51f)
4. **The two test-set log entries of 2026-10-03 were identical** though each ran another
   decoder. Entries now read `via <config> + <decoder>`. (e3e6147)
5. **Per-track files named only the decoder's path**, and `p00-clean-fit.json` names
   `configs/decoder_clean.yaml`, which has held other weights since ADR 0038. New files
   record the split and the weights; the three player-00 files keep the old form. (6631a81)
6. **`compare_validation.py` printed "26446 notes"** for player 00's 13,223: a GuitarSet
   count is estimated plus reference notes, and is now labelled so. (c5946cc)
7. **`measure_lattice.py --guitarset N`** measured at most 60 tracks but labelled them N,
   and its docstring still said it reads and logs the test set. It refuses N above 60.
   (b4946b7)

Corrected on the way: a test comment saying GuitarSet has no validation split (with 1) and

## Task 1 — the errors, by kind

Oracle mode, the default decoder, player 00's 60 tracks: 13,223 notes, 10,664 right — E2's
0.8065 exactly — and 2,559 misplaced, none dropped. Questions 1–6 and their predictions were
committed first (8cdc6d0); question 7 was added after the first run (c4e906f).

| | answer | prediction |
|---|---|---|
| 1 | notes in chords 0.848 right, single notes 0.700 | held |
| 2 | comping 0.871, **soloing 0.598**: 24% of the notes, 49% of the errors. Bossa nova 0.727, jazz 0.749, rock 0.814, singer-songwriter 0.831, funk 0.852 | held |
| 3 | 84% of misplaced notes one string away, 16% two; 43% higher on the neck | held |
| 4 | open strings 0.985, frets 1–4 0.857, **5–11 0.760 (69% of the errors)**, 12+ 0.711; 87% of misplaced notes changed region | — |
| 5 | **the decoder played an open string where the player fretted: 860, a third of all errors**; the reverse, 12 | not predicted |
| 6 | 62% of the errors in runs of four or more | held |
| 7 | for those 860, the decoder's hand and the player's: both at frets 1–4, 362; both at 5 or above, 326; the decoder's at 5+ and the player's at 1–4, 104; the decoder's at 1–4 and the player's at 5+, 68 | **failed**: predicted mostly the last |

**What it argues.** The single largest pattern is an open string where the player stayed in
position and fretted the note; the default rewards every open string (open_reward 0.25)
wherever the hand is. Question 7 says these are rarely a passage moved down the neck: in
688 of the 860 the decoder's hand was in the same region as the player's. Where the
decoder's hand was up the neck — 430 notes, a sixth of all errors, worth at most 3.3 points
of E2 on player 00 — a cost on open strings played there, the Phase 2 plan's "open strings
conditioned on the neighbouring shapes", can reach them. The 362 in open position it cannot:
there an open string and a fretted one are both idiomatic.

**Slip.** The first run counted one right note fewer than E2 (10,663): a unison on two
strings, 3 ms apart in `00_Jazz1-200-B_solo`, paired in order. Copies on the player's string
are now paired first (094356a, with a test); the answers above are from the rerun, which
agrees with E2 exactly.
