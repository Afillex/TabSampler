## A1 — hand movement across all-open chords (ADR 0018)

A lattice node is now a shape plus the hand position carried into it. Only all-open shapes
need the augmentation, and it costs **1.072×** the state count on 6607 groups of real
GuitarSet reference notes (1.104× on transcriber notes) against the 23× that augmenting
every node would cost. The brute-force oracle learned the same carry, spelled out inline
so it stays an independent check, and Viterbi and forward-backward both still agree with
it.

`FingeringScorer` gained `transition_cost_from(previous_hand, curr)`. The plan claimed the
Protocol was unchanged and needed no ADR; that is not possible, because the decoder takes
a Protocol-typed scorer and has to call the new method. ADR 0018 records the contract
change.

### The finding that matters more than the metric

The golden clip moved the phrase 52-55-57-59-60-64-67-72 out of open position and up to
frets 8–12. It is a **genuine minimiser** — 3.667 against 7.383 for the open-position
fingering a guitarist would play — because `move` is 1.0 per fret while `high` is 0.1 per
*octave*, a ratio of **120:1**. Once movement is charged honestly it dominates everything,
so the decoder pre-positions the hand in the middle of the range the phrase will visit.

M1's plausible-looking open-position tab was therefore partly an artefact of the defect:
with movement free across open strings, the emission term (which rewards open strings and
low frets) decided everything. The weights are worse than M1's output suggested.

**Deliberately not fixed.** Reweighting would be tuning with no validation data (ADR 0012)
and, on one hand-picked clip, selection on an example. E2 rose on the corpus, so GuitarSet
does not agree the new output is worse. This is concrete evidence for what the DadaGP /
ProgGP request buys: the `move : high` ratio is the first thing to fit, and the prediction
to test is that `high` rises sharply.

## A2 — barre chords in E3 (ADR 0019)

E3 counted fretted *notes*, so every full barre chord was unplayable. It counts fingers
now: one finger covers every string at the **lowest** fretted fret, and each note above it
costs a finger of its own. M1's E3 group rate was pessimistic by 1.4 points in oracle mode
and 1.5 end to end — real, and smaller than the barre problem's prominence suggested,
because most GuitarSet groups are one or two notes.

The plan's formula ("fingers = number of distinct fretted frets") **contradicts the plan's
own test**: the shape 5,9,9,7,6 has four distinct frets and a 4-fret span, so the formula
passes it, while `test_a_barre_above_the_lowest_fret_does_not_get_the_discount` requires it
to fail. Ruled toward the test, which is also physically right — two notes at fret 9 cannot
be barred while fret 5 is held below them. ADR 0019 records both the rule and why the
alternative was rejected. `max_fretted_notes` → `max_fingers` is config-visible and an old
config now fails with "unknown key", verified by hand.

## A3 — E1 at both measurement points

Settled exactly. E1 on the transcriber's raw output is **0.7437**, which is Phase 0's
recorded figure to the digit; E1 on the notes that survived placement is **0.7452**. The
whole 0.0015 gap was `decode_best_effort` dropping the 158 notes the guitar cannot sound,
which raises precision and leaves recall alone. M1 had been setting the pipeline's number
beside Phase 0's transcriber number and calling them the same metric. Both are 1.0000 in
oracle mode, which is the plumbing check it should be.

## A5 — ADRs 0016 and 0017

- **ADR 0016 is `proposed`, not accepted.** It argues X from the post-A1/A2 baseline, not
  from M1's numbers as the plan's text assumed, and proposes **X = 10 points of oracle
  E2** (0.6599 → 0.760) at M2, with E3/E4/E5 guardrails. End-to-end E2 is bounded above by
  end-to-end E1 (0.7452) until Phase 5, so a target naming only an end-to-end number would
  be a target on `basic-pitch`. **Ege signs off on the single number 10.**
- **ADR 0017 is accepted** and unblocks Task B1: exports use a declared 120 BPM grid at 480
  divisions per quarter, and carry "rhythm is NOT transcribed" *inside the file* where the
  host application shows it. It does not supersede ADR 0009 — the note values are an
  encoding of measured onsets, not transcribed rhythm.

## A4 — the synthetic round-trip diagnostic

`tabsampler diagnose --paths 200 --seed 0`: 3975 notes, round-trip accuracy **0.7293**, of
which 328 (8.3%) had a single legal position and are free wins for any decoder.

**That number must never tune a cost weight or the temperature.** The fingerings it scores
are sampled from our own notion of a plausible shape, so fitting weights to agree with them
would tune the model to agree with its own prior and report the agreement as accuracy. The
warning is in the module docstring, in the command's output next to the number, and here.
It is a diagnostic and a regression test.

## Measurements worth keeping

Both are now reproducible from committed scripts rather than from an ad-hoc paste, which
is what the review found missing.

- **Node lattice growth** (`scripts/measure_lattice.py`): 1.072× on 6607 groups of GuitarSet
  reference notes and 1.104× on 6493 groups of transcriber notes over 60 tracks; 1.30× on a
  synthetic pentatonic run; **3.03×** on the worst case, a line of nothing but open-string
  pitches. The ratio is bounded rather than growing with the piece: a level can carry only
  hand positions earlier groups put the hand in, so the carried set saturates at eight
  values in standard tuning. Full augmentation would be 23×.
- **Decode cost of ADR 0018** (`scripts/bench_decode.py`, run once per commit against its
  own source), 500-group line, warmed, median of seven: `viterbi` 5.5 → 7.2 ms (+31%), full
  `decode` 53.8 → 57.9 ms (+8%).
- **E7 in `results.csv` is not usable for comparison.** The `eval-m1` column measured
  0.0370, 0.17, 0.20 and 0.04 s per audio minute for equivalent decode work on this machine
  in one afternoon. An earlier draft of ADR 0018 quoted "roughly 20%" from two of those
  readings; the ADR was corrected in place with the benchmark above, and says so.

## Open questions and things for Ege

1. **ADR 0016 needs a yes or a different number for X.** Nothing else in it is a judgement
   call.
2. **The `move : high` ratio of 120:1 is the single most valuable thing the dataset request
   would fix.** A1 turned it from invisible into demonstrable.
3. **E3's transition rule does not implement what ADR 0011 says.** ADR 0011: "A group with
   no fretted notes has no hand position, and carries the previous one forward rather than
   resetting to fret 0." `transition_is_playable` instead returns "playable" whenever
   either shape is all-open, so E3 under-reports fast jumps across an intervening open
   chord — the same defect A1 just fixed in the cost model, still live in the metric.

   Reproduced, so it is not a reading of the code but a fact about the metric. Three notes
   50 ms apart, fret 2 → open string → fret 20, which moves the hand 18 frets in 0.1 s:

   | tab | E3 transitions | verdict |
   |---|---|---|
   | `(0,2)` @0.00, `(1,0)` @0.05, `(0,20)` @0.10 | 2/2 | **passes** |
   | `(0,2)` @0.00, `(0,20)` @0.10 | 0/1 | fails, "180.0 frets/s exceeds 12.0" |

   The identical hand movement is playable or not depending only on whether an open string
   is struck in between. **Not fixed here**: it would move E3's transition rate in the same
   commit as A2's group rate and break one-variable-per-experiment, and choosing between the
   ADR's text and the metric's behaviour is a decision, not a bug fix. Worth its own task,
   and the fix is the one A1 already worked out — thread the carried hand through
   `playability_rate` rather than deciding per pair of shapes.
4. **`load_phase1_config` and `load_eval_config` have no tests.** The `max_fingers` rename
   is safe — verified by hand that the old key is refused — but nothing pins it.
5. **`eval-m1` writes the *config's* hypothesis into `results.csv`**, so the Phase 1.5 rows
   carry M1's hypothesis text. Numbers and commits are right; the hypothesis column is
   stale. A `configs/phase15_full_eval.yaml` would fix it, but how the results table is
   organised is Ege's call.

## What the fresh-context review changed

One reviewer, fresh context, over the whole branch. No Critical findings: it could not
construct an input that makes the decoder wrong, produce a nan, or make a logsumexp level
`-inf`, and it independently reproduced ADR 0018's worked example (3.6667 against 7.3833) to
the digit. Five Important findings, all real, all fixed in one pass:

1. **A test that could never fail.** `test_a_forbidden_node_transition_carries_no_weight`
   built its "reachable" set as a cross-product, so the set always contained every node's
   carried hand and **zero assertions executed**. Replaced by a direct unit test of
   `node_transition_cost` on a hand-built teleporting node, plus a test that `inf`
   transitions leave the posteriors finite and summing to 1. Both were mutation-checked:
   deleting the guard fails them, and fails all five oracle tests too.
2. **A wrong measured claim in an accepted ADR.** ADR 0018 gave the worst-case lattice
   growth as 1.74×, measured on a line that mixed open-string pitches with ordinary ones and
   so diluted the effect. The real worst case is **3.03×**, and the test named
   `..._worst_case_...` was asserting a 2.0× bound the true input breaks. Corrected, with
   the saturation mechanism that bounds it now stated and pinned by a test.
3. **E3 accepted a shape needing five fingers.** The barre discount charged one finger for
   every note at the lowest fret regardless of which strings they sat on, so low E at fret 5
   with the A string **open** and the D string at fret 5 counted as one finger. A barre lies
   flat and would press the open A. Fixed: the discount now requires no open string inside
   the barre's run of strings; a string fretted *higher* inside the run is still fine, which
   is what makes an E-shape barre work. This moved E3 groups by −0.0001 in both modes
   (0.9971 → **0.9970** oracle, 0.9897 → **0.9896** end to end) — small, and in the honest
   direction. Review Focus 5 asked exactly this question and the answer was yes.
4. **The config loaders had no tests at all.** Added `tests/test_config.py`, whose strongest
   test asserts every field of `PlayabilityRules`, `CostWeights` and `Tuning` is reachable
   from a config file. That is the test that catches a key missing from a
   `_require_known_keys` tuple — a mistake that rejects every user config while CI, whose
   committed configs set none of those keys, stays green. Mutation-checked by deleting
   `allow_barre` from the tuple.
5. **Four numbers with no committed provenance.** The decode benchmark and the lattice
   ratios lived only in prose. Added `scripts/bench_decode.py` and
   `scripts/measure_lattice.py`, re-measured with them, and recorded the benchmark in
   `experiments/results.csv`. Chunk A's gate asks that every number be traceable to an
   executed run; a committed script is what makes it re-runnable.

### Deferred, deliberately — none of these was acted on

Each is real. None changes what a user gets today, so they are recorded rather than fixed,
and the decision to defer is mine to be overruled on.

1. `node_transition_cost` re-derives `ChordState.hand_position` twice per (prior, node)
   pair, and that is a plain `@property` that re-sorts `fretted_frets` on every access. At
   `O(S²)` per step this is probably most of Viterbi's +31%. Fixable by computing an
   is-all-open flag once per node in `build_lattice`.
2. `forward_backward` changed the **meaning** of its return indices — nodes now, not states
   — while keeping its name and signature. No caller outside the module today, but Chunk B
   or Phase 2 code that pairs it with `enumerate_states` would be silently wrong. Renaming
   it `node_posteriors`, or returning the nodes alongside the arrays, would make that
   mistake unrepresentable.
3. `FingeringScorer.transition_cost` now has no production caller (the Protocol plus tests),
   so the contract asks every future learned scorer for a method the decoder never calls.
   ADR 0018 argues for keeping it; worth revisiting when the Phase 2 scorer lands.
4. `round_trip_accuracy` sets `n_paths=len(paths)` but skips empty paths, so the count can
   disagree with what the notes were aggregated over.
5. The A4 sampler draws at most 4 notes per shape, so the diagnostic **never generates the
   5- and 6-note barre shapes A2 just legalised**. It matches the plan's "pick 1–4 strings",
   but it means the diagnostic does not exercise the case ADR 0019 was written for. Its
   `if fret > tuning.max_fret` branch is also unreachable given the hand bound.
6. `test_a_sampled_group_is_ordered_and_matches_its_state` asserts neither ordering nor
   note↔position alignment, only lengths and string distinctness. The misalignment its
   comment warns about is caught by the pitch round-trip test instead.
7. `test_the_two_e1_rows_agree_when_nothing_is_dropped` passes `mode="oracle"`, but `mode`
   is only a label in `evaluate_full`; the "every note is playable" property comes from the
   test's own `notes_in`. The assertion still means something.
8. ADR 0016's "design effect of 10" is asserted, not measured, and it carries the whole
   "half a point is noise, two points is real" conclusion. `FullReport.tracks` already holds
   the per-track E2 needed to estimate it properly.
9. `tabsampler diagnose` raises `UnfingerableGroupError` on any config with
   `max_span < rules.max_span_high`. Documented as caller error; the committed config is 5/5.
10. Pre-existing, outside this branch's diff: `log_beta` aliases one array across all levels
    before overwriting every element; `log_partition` does not validate `temperature > 0`
    while `forward_backward` does; `build_lattice` is called three times per `decode`.

**Two accepted ADRs were amended in place**, both written earlier in this same session on
this unmerged branch: 0018 twice (a decode-time claim derived from E7 noise, then the
worst-case row) and 0019 once (the barre-reach rule). The project rule is never to edit an
accepted ADR, and "never invent results" outranks it — but stated broadly that licence is
how accepted ADRs start drifting. Narrowed: **correcting an ADR in place is only acceptable
before the branch carrying it has been reviewed, and each correction says in the ADR that it
happened.** After that, supersede.
